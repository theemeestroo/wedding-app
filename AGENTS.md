# Wedding Decision Platform — Agent Guidelines

## Product Overview

See [wedding-decision-platform-prd-v0 4.md](wedding-decision-platform-prd-v0%204.md) for the full PRD. In short: a collaborative platform that helps couples compare wedding options (guest list → travel feasibility → venue → cost) before committing to one — not a post-decision planning tool.

## Architecture Rules

- **Shared Supabase project, not a shared app**: this app uses the same Supabase project as Letly (`letly/`, a separate repo), isolated by Postgres schema (`NEXT_PUBLIC_APP_SCHEMA=wedding`). `auth.users` is the one thing genuinely shared — everything else (tables, RLS, workspace/membership model) belongs to this app alone. See `letly/supabase-schema-split-plan.md` in the Letly repo for the full rationale.
- **Signup metadata**: `supabase.auth.signUp()` calls from this app must include `options.data.app = 'wedding'` (see `components/auth/signup-form.tsx`) — the shared `handle_new_user()` trigger uses it to skip Letly's org-provisioning branch.
- **Workspace provisioning is this app's own responsibility.** Nothing about weddings, guests, or venues should ever be created by a database trigger shared with Letly — provision via this app's own schema-scoped `lib/supabase/admin.ts` client, in this app's own code.
- **i18n routing**: same `[lang]` pattern as Letly — locale-aware routes live under `app/[lang]/(group)/`. Translations live in `messages/{en,de,fr}.json`; run `npm run i18n:sync` after adding keys to `en.json` (requires `DEEPL_API_KEY`).
- **Bare (non-`[lang]`) route pairing is `(auth)`-only.** `proxy.ts` redirects every bare path to its `/{locale}` equivalent before Next.js resolves it, so a bare page is unreachable by real traffic — it only exists as dead weight unless something specifically needs it. The `(auth)` pages (login/signup/reset-password/accept-invite) keep bare English-only counterparts because they were carried over from Letly's convention; every other route group (`(app)`, and anything after it) is `[lang]`-only. Don't add new bare pages outside `(auth)` without a real reason.
- **Projects, not organisations.** The tenancy unit is `wedding.projects` (a couple), not an org — `wedding.project_members` (`owner`/`partner`/`viewer`) and `wedding.is_project_member()`/`is_project_owner()` mirror Letly's org-RLS shape. `wedding.create_project()` and `wedding.accept_project_invitation()` are `security definer` because RLS can't authorize the very first membership row for a project that has none yet — see the comment at the top of `supabase/migrations/20260817120000_phase0_foundation.sql`.
- **Partner invites are copy-a-link, not app-sent email**, deliberately — same reasoning the PRD gives for venue enquiries (§12): app-sent mail from an unverified domain is a liability, a link isn't. `wedding.project_invitations` holds the token; `/auth/accept-invite?token=` previews it via `app/api/invitations/[token]/route.ts` (admin client — the visitor isn't a project member yet, so RLS can't authorize that read) and accepts via the RPC once authenticated.
- **This repo owns its own migrations** in `supabase/` (linked to the same project as Letly, `project-ref prycwxeojswobkmkrsiw`). Apply with `supabase db query --linked --file <path>` — the CLI's migration ledger is out of sync with what's actually been applied (established while building Phase 0), so `supabase db push` isn't safe to use yet.
- **Every venue-scoped table's RLS goes through `wedding.venue_project_id(venue_id)`** (defined in `supabase/migrations/20260817140000_phase1_venue_board.sql`), not a raw subquery repeated per policy. Any new table hanging off `venues` should reuse it the same way `venue_sources`/`venue_facts`/`venue_contacts`/`venue_documents` do.
- **Documents live in the private `wedding-documents` Storage bucket**, path `{project_id}/{venue_id}/{filename}` — the leading path segment is what the bucket's RLS policies check via `storage.foldername(name)`, so any new document-producing feature must keep that convention or its own RLS policy.
- **New venue-adjacent server routes that fetch arbitrary user-submitted URLs must keep the SSRF guard** `app/api/venues/og/route.ts` established (reject non-http(s) schemes and private/loopback/link-local hostnames) — don't fetch a user-submitted URL server-side without it.
- **Every venue always has exactly one enquiry.** A trigger on `wedding.venues` (`supabase/migrations/20260817160000_phase2_enquiry_crm.sql`) creates the `wedding.enquiries` row automatically on insert — never create a venue and its enquiry as two separate app-level steps, and never add a way to delete an enquiry independently of its venue (no delete policy exists on purpose). `wedding.enquiry_project_id(enquiry_id)` extends `venue_project_id()` one level for `enquiry_events`/`quotes` RLS.
- **The inbound-parse email address (PRD §12) is deliberately not built.** It needs a domain that can receive mail plus an inbound-parsing provider account, neither of which exist for this project. Don't build toward a specific provider without asking first — this was an explicit user decision, not an oversight.
- **No app-sent email anywhere in this app.** Both the partner-invite flow (Phase 0) and the enquiry draft-message generator (Phase 2) deliberately stop at "copy the text / open a `mailto:` link" rather than sending on the user's behalf — same reasoning each time (unverified sending domain), stated explicitly in the PRD for enquiries (§12) and applied consistently elsewhere. Keep new outbound-communication features to this shape unless a real email provider gets configured.
- **Tier and group are household-level, not per-guest.** PRD §7's data model tree reads `Guest ── Household ── Tier` — a household shares one tier and one optional `group_label`; only name and the child flag vary per guest within it. Don't add per-guest tier/group fields without revisiting this.
- **Tier is a per-project, user-managed set of named categories (`wedding.tier_definitions`), not a fixed A–D enum.** Originally shipped as a hardcoded `households.tier text check (tier in ('A','B','C','D'))` (Phase 3); replaced because a bare letter with no legend anywhere was flagged as confusing. `households.tier_id` is a nullable FK (`on delete set null`, same shape as `origin_cluster_id`/"Unassigned" — no delete-guard, deleting a tier a household used just clears it) and `guest_plans.included_tier_ids uuid[]` replaces the old `included_tiers text[]` the same way. Every project (existing, backfilled, and new, via `wedding.create_project()`) starts with 4 seeded defaults ("Must invite" / "Should invite" / "Could invite" / "If space allows") that a couple can rename/reorder/add/delete from Settings → Manage tiers (`app/[lang]/(app)/settings/tiers/page.tsx`, `components/settings/tier-manager.tsx`). A `tiers: TierOption[]` (`{id, label, sortOrder}`, defined in `components/guests/household-card.tsx`) is threaded down as a prop everywhere a tier picker or label display is needed — the same shape `ClusterOption` already used for origin clusters — rather than re-fetching per component. See `supabase/migrations/20260818120000_phase3_tier_definitions.sql` (expand: adds the new columns, backfills, leaves the old ones in place) and its follow-up `..._cleanup.sql` (contract: drops `households.tier`/`guest_plans.included_tiers` — only run once the new app code is confirmed live) for why this shipped as two migrations instead of one; this was the first migration in the repo to transform and retire existing data rather than purely add to the schema.
- **`guests.rsvp_status` is per-guest, not per-household** (`not_invited`/`invited`/`attending`/`declined`, added in `supabase/migrations/20260819110000_guest_rsvp_status.sql`) — the one deliberate exception to "tier and group are household-level" above, because unlike tier/group, whether someone actually comes is a genuinely per-person fact (one child in a household can decline while the rest attend). It's a manually-set status the couple update themselves as they hear back through whatever channel they use — **the app never sends an invitation and this isn't a scope change** toward the PRD §18 "out of scope" RSVP/invitations feature, just a status record layered on top of a guest list that was always going to outlive the decision phase. Deliberately informational: `lib/guest-plan.ts`'s `isHouseholdIncluded`/`sumHeadcount` and the cost engine keep using full invited headcount regardless of RSVP status, the same stance `lib/attendance-engine.ts`'s decline-rate heuristic already takes. `components/guests/rsvp-status-control.tsx` is the shared badge/select; `household-card.tsx` also gets a bulk "mark all attending" per household.
- **Household `group_label` stays free-text** (groups are ad-hoc and couple-invented, unlike tier) **but is offered as a suggestion list, not managed like tiers.** `guests/page.tsx` derives `existingGroups` from the project's own already-fetched households (`Array.from(new Set(households.map(h => h.group_label).filter(Boolean)))` — no separate query) and every group input renders it via a native `<input list="..."> + <datalist>` combobox, which both suggests previously-used groups and still accepts a freshly-typed one. Don't extend this same datalist pattern to `plan-form.tsx`'s groups field without solving a different problem first — that field is a *comma-separated multi-value* string, and `<datalist>` only ever matches an input's entire current value, so it silently stops suggesting after the first comma; a real multi-value picker there needs a small chip UI, not a reused datalist.
- **Origin clustering only ever buckets households with `origin_cluster_id is null`.** `wedding.recompute_origin_clusters()` (`supabase/migrations/20260817180000_phase3_guests_plans.sql`) never reassigns a household that already has a cluster — that's the entire mechanism protecting a couple's manual correction from being silently overwritten by a later recompute. Don't add logic that reassigns already-clustered households without also solving that protection problem properly (a "manually pinned" flag, most likely).
- **The geocode cache (`wedding.geocode_cache`) is global, not project-scoped, and has zero RLS policies on purpose.** `authenticated`/`anon` get nothing; only `app/api/geocode/route.ts`'s admin client (which bypasses RLS) ever touches it. Never query it directly from a browser client — go through that route, which also respects Nominatim's 1 req/sec usage policy for you.
- **Project deletion removes Storage objects before deleting the DB row** (`components/settings/delete-project.tsx`) — Postgres cascades handle every table under `projects`, but `wedding-documents` objects aren't FK-linked, so they need an explicit recursive `list()`/`remove()` walk first (folders show up as `list()` entries with `id: null`, real objects have a non-null `id` — verified live, not just assumed). Any future feature that deletes a venue or project must account for this the same way.
- **An Option is full multi-day**, a deliberate scope decision (not the PRD §7 sketch's single-date model): `wedding.options` is a bare container, `wedding.option_events` holds its dated sub-events (welcome dinner / wedding day / farewell brunch / other), and a trigger guarantees exactly one `is_primary` `wedding_day` event exists from creation — same invariant-by-trigger pattern as Phase 2's venue→enquiry. Don't add a `date` column to `options` itself; the date belongs to an event.
- **`wedding.cost_rules` ownership is three nullable FK columns (`venue_id`/`guest_plan_id`/`option_id`) with a check constraint requiring exactly one**, not a polymorphic `(owner_type, owner_id)` pair — verified live that both zero-owner and two-owner inserts are rejected. RLS is `coalesce()` over the three existing `*_project_id()` helpers; don't add a fourth owner type without extending that coalesce chain.
- **A cost rule's `event_type` column is independent of its ownership** — it says which event's headcount to evaluate against (falling back to the full guest-plan headcount if the Option has no matching event), not where the rule is defined. A venue-owned rule with `event_type = 'welcome_dinner'` is still reusable across every Option on that venue; it just evaluates differently per Option depending on whether that Option has set up a welcome-dinner event.
- **The cost engine (`lib/cost-engine.ts`) is plain TypeScript, not a Postgres function** — real branching logic (event-context resolution, two-pass `percent_of_subtotal`, confidence→range), a deliberate choice over a large plpgsql function for what the PRD calls the riskiest phase of the build. Postgres only owns storage/RLS/the primary-event trigger. Verified by running the exact numbers from `implementation-plan.md`'s paper prototype through the real function (not just re-deriving them by hand) — a €17,800 mid total, €12,480–23,120 range, and a €5,040 range-narrowing from confirming the "biggest unknown" line, all matched exactly.
- **`applies-when` (PRD §9.1) is guest-count thresholds only in v1** (`cost_rules.min_guests`/`max_guests`) — not a general condition-expression engine. A rule outside its guest-count bounds is silently excluded from the total (correct — the condition just isn't met), which is different from an *unevaluable* rule (missing `rooms`/`nights`/`hours` it needs), which is shown to the user, not silently zeroed or dropped.
- **`lib/guest-plan.ts`'s inclusion logic is shared between the Plans page and the cost engine** — extracted from `components/plans/plan-card.tsx` in Phase 4 specifically so a second consumer wouldn't re-derive "which households are in this plan." Any change to inclusion/exception logic belongs there, not back in a component.
- **The Journey/Gateway engine (`lib/journey-engine.ts`) is plain TypeScript, not a Postgres function or table** — same reasoning as the cost engine: cheap, deterministic math given two sets of coordinates, no external calls at request time (geocoding is already cached — see below). `wedding.venues` only gained `latitude`/`longitude` columns (Phase 5 migration); there's no `journeys` table. Real data, not fabrication: `lib/data/airports.json` is 3,270 rows filtered from OurAirports (public domain) to `large`/`medium` airports with scheduled service and a real IATA code — that's genuine airport-classification data. What is **not** claimed is that a specific flight route exists between two specific airports; connection count is a heuristic off real airport-size classification plus flight distance, always surfaced at `guess` confidence. Don't add a "does route X→Y exist" claim without a real, licensed route-data source — the PRD's own §10.6 v1 guidance only expects this same kind of static heuristic, not verified live routes.
- **The visual map (PRD §11) is deliberately deferred** — Phase 5 shipped the underlying data (guest-hours, difficulty bands, the who's-it-hard-for list, Compare, break-even chart, Decision Session) without any map visualisation. Not forgotten — a real scope decision, same treatment as Phase 2's inbound-email deferral. A future phase can add it (lightweight SVG or full MapLibre+MapTiler).
- **Phase 3's origin clustering was *not* replaced or upgraded in Phase 5** — despite an earlier note in this file suggesting it would be. `wedding.recompute_origin_clusters()`'s grid-bucket heuristic (`floor(latitude/2), floor(longitude/2)`) is still what Phase 5's Journey engine consumes as input; the Gateway/airport work sits entirely downstream of it (cluster centroid → nearest real airport → venue), not as a replacement for how clusters themselves get formed.
- **Ratings' blind-until-you-commit reveal is enforced by RLS, not the UI** (`wedding.ratings`, Phase 5 migration) — a member can always read their own rating; they can read someone else's rating for an option only once they've submitted their own rating for that same option. A plain inline subquery for "have I already rated this" causes Postgres to reject the policy with "infinite recursion detected" (confirmed live) because it self-joins the table the policy is on — the fix is the same `security definer` wrapper-function pattern used everywhere else (`wedding.has_rated_option(option_id)`), not a client-side hide. Reuse this pattern (helper function, not inline self-join) for any future table whose own RLS needs to query itself.
- **`profile_id`/`decided_by`-style "who did this" columns should default to `auth.uid()` at the column level**, not rely on the client to send it — `wedding.ratings.profile_id` and `wedding.decisions.decided_by` both do this (the latter fixed live during Phase 5 verification after a first pass omitted it and decisions came back with `decided_by: null`). The `with check`/`using` clause still enforces it can't be spoofed to someone else's id; the default just means the app code doesn't have to thread the current user's id through every insert.
- **Accommodation is room-level, not property-level (Phase 7b).** `wedding.accommodations` is the property record only (name/type/confidence); `wedding.accommodation_rooms` is the actual bookable unit — capacity, room type and nightly rate all live on the room, not the property, because different rooms within one hotel/villa can differ. "Block create" (the Venue → Accommodation tab's room form) is an app-level insert of N rows sharing type/capacity/rate with auto-numbered labels, not a `quantity` column — every room is its own row from creation so it can be independently allocated. `wedding.allocations` points at a specific `room_id` (not `accommodation_id` + a bare count); a household needing multiple rooms just gets multiple allocation rows. `unique(option_id, room_id)` is the DB-level guarantee a room can't be double-booked within one Option — the room pickers in `components/options/option-accommodation-tab.tsx` only ever offer unbooked rooms, but the constraint is the real backstop. `wedding.accommodation_room_project_id(room_id)` extends `venue_project_id()` two levels (room → accommodation → venue), same pattern as `enquiry_project_id()`/`option_project_id()`. `lib/accommodation-engine.ts`'s `computeRoomOccupancy()` is the pure-TS lookup behind the "N/M rooms booked" badge. This replaced Phase 7's original flat `rooms_available`/`capacity_adults`/`capacity_children`/`nightly_rate` columns on `accommodations` — that shape couldn't represent more than one room type per property and had no way to prevent two households being counted against the same physical room.
- **Accommodation can be priced as a whole block instead of per room (Phase 7c).** Phase 7b's room-level model can't represent a venue that quotes exclusive use of the entire property as one number regardless of room split — confirmed against a real venue proposal (Ca' Salva: "EUR2,000/night, exclusive use of all 21 beds", never priced per apartment) entered into a real project 2026-08-20. `wedding.accommodations` gained `pricing_mode` (`'per_room'`, the default, preserving Phase 7b's behaviour exactly — cost lives on each room's `nightly_rate`; or `'block'` — cost is `block_nightly_rate`/`block_currency` on the accommodation itself), with a check constraint requiring the block rate when the mode is `'block'`. `wedding.accommodation_rooms.nightly_rate` became nullable — under a block-priced accommodation, rooms are pure allocation/labelling records (which named apartment a household is in) with no cost meaning of their own. `lib/accommodation-engine.ts`'s `computeAccommodationCost()` takes a new `accommodations: AccommodationInput[]` argument and groups allocations by their room's parent accommodation: per-room allocations price exactly as before (unchanged), block-mode allocations are priced once per accommodation (not once per allocation — the property costs the same whether one guest or twenty are in it) over the span from the earliest arrival to the latest departure among everyone allocated to it, same 2-night default as the per-room path when no one has an arrival profile set yet. No change to how that total reaches the option's cost total — it still goes through the existing Phase 7 "Estimate accommodation & transfer costs" button, which upserts a `fixed` `cost_rules` row exactly as before. Verified live end-to-end (real project, real login via an admin-generated session — the app's `/auth/callback` route is PKCE-only and doesn't handle `admin.generateLink()`'s implicit-flow output, so verification completed the magiclink token server-side and set the `@supabase/ssr` session cookie directly): adding a block-priced accommodation, adding a room with a blank rate, allocating a household to it, and clicking "Estimate costs" produced "Accommodation (auto-calculated): EUR4,000" (EUR2,000 x the 2-night default) with zero console errors. Test data was removed afterward — this wasn't left in the couple's real project.
- **The Compare page (`app/[lang]/(app)/compare/page.tsx`) computes every option's cost/logistics summary server-side**, including the break-even chart's data points (a fixed guest-count sweep, 20→150, through `computeOptionCosts` per point) — the client component (`components/compare/compare-board.tsx`) only does selection state and rendering (Recharts), never re-fetches or re-derives. It intentionally does **not** break costs down by category (Venue/Catering/Accommodation as separate comparable rows) — `cost_rules` has no `category` dimension yet, and adding one just for this comparison view would be scope creep; the total-range-plus-link-to-full-breakdown covers the job.

## Current State

Phases 0 (Foundation) through 5 (Logistics and Compare) are built and verified end-to-end against the live Supabase project — see [implementation-plan.md](implementation-plan.md) for exactly what each phase covers. Auth, locale routing, projects/membership/invites, the venue board, the enquiry pipeline, households/guests/origins/plans, multi-day Options with the full rule-based cost engine, and now the Journey/Gateway logistics engine, the Compare page with a break-even chart, and the Decision Session (blind-reveal ratings + owner-gated decision recording) all work. Phase 3's origin clustering is unchanged by Phase 5 — still the grid-bucket heuristic, now feeding the Journey engine as its input rather than being replaced by it.

Phase 7 is now **fully built** (skipping Phase 6 — AI structuring is still not started; the plan's own sequencing note says 6 and 7 aren't load-bearing for each other): `wedding.accommodations`/`wedding.arrival_profiles` (incl. self-reported `visa_notes`)/`wedding.allocations` plus `lib/accommodation-engine.ts` (room-night/transfer cost estimation), `lib/burden-surface-engine.ts` + `lib/contour-utils.ts` (the travel map's burden surface, coverage rings, centre of gravity — see the map bullet below), and `lib/attendance-engine.ts` (informational-only attendance forecast). Full details in implementation-plan.md's Phase 7 entry.

**The travel map (PRD §11) lives inside Compare's new Table/Map view toggle** (`components/compare/compare-board.tsx`), not a separate route — plain `maplibre-gl` (no `react-map-gl`), `NEXT_PUBLIC_MAPTILER_KEY` in `.env.local` for the vector basemap. All five layers are real computed data (an adaptive ~300-point grid for the burden surface, `d3-contour` for real contour polygons, true-circle coverage rings with real coverage percentages per PRD §11.3's own sanctioned v1 shortcut, great-circle flow lines, and live drop-a-pin). `lib/journey-engine.ts` gained a small additive refactor (`computeJourneyFromAirports()` extracted from `computeJourney()`, plus a few newly-exported helpers) so the grid engine reuses the exact same journey-cost formulas instead of duplicating them — no behaviour change to any existing caller. **Not visually confirmed end-to-end**: a real authenticated browser walkthrough (throwaway test account + project, cleaned up afterward) confirmed the surrounding UI and all computed data render correctly, and MapTiler's style/sprite/tile endpoints all respond 200 against a correctly-sized canvas with a working WebGL2 context, but MapLibre's render loop never visually painted in this environment's headless testing — no error anywhere (not in the app, not in MapLibre's own error events), consistent with a known headless/software-WebGL limitation for GPU-heavy libraries rather than an app bug. Check in a real browser before relying on it.

Legal ceremony feasibility (the venue/country-level half of "visa/legal tracking") deliberately has **no dedicated feature** — it's the same shape as an existing `venue_facts` row or the `venues.notes` tab, and building a duplicate of something that already exists wasn't worth it. No licensed regulatory dataset exists for either visa requirements or legal feasibility — the app never computes or asserts either, only stores what a couple types in, same honesty stance as the flight-route data in Phase 5.

The app is branded **The Wedding Lab** (rebranded from the earlier "Aisle" placeholder identity) with a "Grand Regency" visual identity — Midnight Plum (`--primary`, `#2d1b2e`), Burnished Gold (`--gold`, `#c5a059`) and Soft Parchment (`--background`, `#fff7fb`), sharp `0`-radius structural containers (`--radius: 0rem`, so `rounded-full` avatars/badges are the deliberate exception, not affected by the token), and hairline gold borders by default (`--border`/`--input`/`--ring` are translucent gold, not neutral grey) — all wired as CSS custom properties in `app/globals.css`, so this is a token-only re-skin that automatically re-themes the whole app (colours, borders, corner radius) without touching most individual components. Playfair Display for headings (`font-heading`) and Manrope for body/UI text, loaded via `next/font/google` in `app/layout.tsx`. Dark mode inverts to the deep-plum "night" surface (`#140516`) the brand's own dark reference pages use, with gold staying the one accent colour in both modes; it's fully wired but has no UI toggle yet (`components/theme-provider.tsx`'s `useTheme()` is dead code — see the lint note below). New `globals.css` primitives: `.btn-primary`/`.btn-secondary`/`.btn-tertiary` and `.input-regency` (the shared button/input treatment — plum fill with a gold hover border, transparent-with-gold-border, underline, and bottom-border-only respectively — applied app-wide, not just on the marketing/auth pages), `.ambient-shadow` (diffused plum-tinted elevation shadow), `.gold-gradient-text` (metallic gold gradient for headline/wordmark accents on dark surfaces), `.ink-band` (a fixed Midnight Plum full-bleed section for statement moments — deliberately *not* theme tokens, with a `.dark` override one step darker so it doesn't flatten into an already-dark page), and `.numeral-ghost` (oversized translucent serif numerals for step counters, carried over from the previous identity). `components/logo.tsx` renders the brand's wax-stamp mark (`public/brand/logo-{light,dark}-stamp.png`, swapped via `dark:`) circular-cropped with a hairline gold border, replacing the earlier CSS ampersand badge; `app/icon.png` (a tighter crop of the dark stamp) is the favicon via Next's file-convention auto-icon. `components/marketing/home-page.tsx` is the real marketing homepage (hero, how-it-works, feature grid, closing CTA) rendered by both `app/page.tsx` and `app/[lang]/page.tsx`. Swap the token values in `app/globals.css` if the brand direction changes again; nearly every component consumes semantic tokens (`bg-background`, `text-primary`, `border`, etc.) rather than hardcoded colors.

The visual identity is deliberately without any real photography (none is licensed for this app; see `components/shared/`'s doc comments) — the wax-stamp mark itself stands in as the brand's "photograph". `components/shared/arch-panel.tsx` is a sharp-edged Midnight Plum panel (hairline gold border, a large centred stamp, gold label-caps eyebrow, gold-gradient-text tagline, gold laurel divider) that stands in for the framed photography reference sites in this space lean on; it takes an `align` prop (`'start'` keeps its mark clear of an overlapping card, `'center'` for when it stands alone) and is reused on the marketing hero and both auth layouts (`app/(auth)/layout.tsx` / `app/[lang]/(auth)/layout.tsx`, a desktop split-panel — decorative panel + form — collapsing to a centered card below `lg`). `components/shared/laurel-divider.tsx` is a small hand-drawn SVG sprig flanking section headings, now rendered in gold. Semantic-meaning elements — `confidence-badge.tsx`, `enquiry-status-badge.tsx`, the household tier wax-seal circle badges in `household-card.tsx` (`TIER_STYLES`), map legend colours, and the compare-board/recharts chart colours — were deliberately left on their own accent hues rather than reskinned to gold/plum, since those colours encode meaning (confidence level, status, tier), not brand decoration; they inherit the new base tokens (background/border/text) automatically.

Two pre-existing lint issues predate this work and weren't introduced by it — don't be alarmed by them, and don't casually "fix" them without checking why they're there first: `components/theme-provider.tsx` deliberately sets state inside an effect (avoids a hydration mismatch against the inline theme script that runs before React hydrates — the newer `react-hooks/set-state-in-effect` rule doesn't know that); `app/(auth)/error.tsx` / `app/[lang]/(auth)/error.tsx` have an intentionally-unused `error` prop (Next's error boundary signature requires it even though the UI doesn't display it).
